# 内网部署：点运行后「卡住不动」的排查

典型现象（2026-10-27 内网实例实测）：

- 任务「分析一下这个项目」，第一轮助手调了 `list_files({})`，返回 `count:200, truncated:true`；
- 紧接着又调了一次 `list_files({})`，被框架以「重复调用」拦下（0ms）；
- 之后页面几分钟没有任何变化，右侧时间线停在那条「重复调用」上，看起来像卡死。

**结论：不是死锁，也不是工具坏了。** 是上下文太大 + 内网机器纯 CPU 推理，
一次模型调用就要几分钟；「重复调用」被拦是对的，但旧文案没告诉模型接下来该怎么走。

## 一、根因（三条叠加，缺一条都不会这么久）

1. **首个工具结果体积过大。** 旧的 `list_files` 是递归遍历、无深度控制，在 demo-project（915 个文件）
   根目录一次吐出 200 条、约 **20.7KB**。更糟的是深度优先，前 200 条几乎全耗在某一个深层目录里，
   模型看不到「工程长什么样」，只看到一堆散文件。
2. **这笔体积是永久账。** 工具结果进历史后，**之后每一次**模型调用都要重新处理这约 1 万 token。
   日志实测：第一次调用 41s，加入 20KB 结果后下一次调用变成 **4 分 58 秒**。
3. **机器是纯 CPU。** `ollama ps` 显示 `100% CPU`（qwen2.5:7b 6.0GB / 32k ctx，无 GPU），
   prompt 处理约 30–50 tok/s、生成约 3–5 tok/s。5 分钟一次调用是硬件真实速度，不是 bug。
   而这段时间页面收不到任何 SSE 事件，于是「看起来卡死」。

第 4 条把用户钉在原地：模型想多看一点，又原样重调一次 → 被拦截 → 旧文案只说「用上一次的结果」，
没说「换参数就能继续」，小模型就僵在那里，白等一整轮（几分钟）。

## 二、已做的修复

| 位置 | 改动 |
| --- | --- |
| `CodeFilesTool.listFiles` | 新增 `depth` 参数（默认 1 层，最多 5 层）；遍历改为**广度优先**，截断时也先给浅层结构；截断/浅层时返回 `hint` 明确指路 |
| `ChatAgent` 重复调用拦截 | 文案补上「truncated=true 想看更多就换参数（`dir`/`depth`/`from`/`to`），参数不同不会被拦」 |
| 前端 `App.tsx` | 等待心跳：运行中 5 秒没有新事件，状态栏显示「等待模型 45s（首次或长上下文时较慢）」 |
| `CodePrompt` | 工具说明同步为「默认只列一层，depth 控制层数」 |

## 三、修复前后实测（同一工程、同一任务、同机同模型）

| 指标 | 修复前 | 修复后 |
| --- | --- | --- |
| 根目录 `list_files` 输出 | 200 条 / 20.7KB（truncated） | **9 条 / 716B**（结构清晰：README、frequencyAnaly、logs…） |
| 加入首个结果后的单次模型调用 | 4 分 58 秒 | **45 秒** |
| 第二次工具后的模型调用 | — | **21 秒** |
| 重复调用 | 1 次（被拦，白等一轮） | **0 次**，模型改为 `dir=frequencyAnaly` 往下走 |
| 全程 | 10 分 38 秒 / 6 分 06 秒 | 5 分 28 秒（3 次工具调用全部有效） |

修复后剩下的 5 分半，几乎全是「读完 479 行 pom.xml 后生成 735 字回答」的 CPU 生成时间，
这部分靠代码改不动，只能换模型或加硬件。

## 四、内网机器怎么再快一点

按收益从大到小：

1. **换小模型。** `qwen2.5:3b`（或同量级 4B）在 CPU 上通常是 7B 的 2–3 倍速度，
   工具调用这种结构化任务 3B 足够；把最终写作交给更大的模型也可以（见 `model.summarizer.*` 两套模型配置）。
2. **把上下文降下来。** `OLLAMA_NUM_CTX=8192`（默认 32768 只按最大预算分配 KV，
   实际用不满反而占内存）。注意：上下文太小会把长文件截断，`read_file` 单次上限 800 行就是为此设的。
3. **有 GPU 就指过去。** 把 `model.base-url` 指向内网那台带 GPU 的 Ollama；
   判断方式还是 `ollama ps`，`PROCESSOR` 显示 GPU 才算真的用上。
4. **别让模型被换出。** `OLLAMA_KEEP_ALIVE=-1`（`ollama ps` 里 UNTIL 应是 `Forever`），
   否则冷启动还要再等几十秒加载 6GB 权重。

## 五、下次怎么快速判断「是卡死还是慢」

```bash
# 1) 模型在不在、用没用 CPU/GPU
ollama ps

# 2) 看在跑还是已结束：日志每行都有秒级时间戳
#    （Windows 控制台输出是 GBK，用 iconv 转一下）
iconv -f GBK -t UTF-8 target/serve-8097.log | tail -20

# 3) 服务本身是否活着
curl -s --noproxy 127.0.0.1 http://127.0.0.1:8097/api/health
```

判断标准：日志里**上一条 `← 返回` 与下一条 `→ 调用` 之间的间隔**就是这次模型调用的耗时。
间隔在几十秒到几分钟且服务 `/api/health` 正常 = 只是慢；服务无响应或日志完全停住才是卡死。

## 六、模型选型：内网 CPU 上的实测对比

同一台机器（20 核、无 GPU）、同一任务「分析一下这个项目」、同一工程 `D:/workspace/demo-project`
（915 个文件）、同样走 `general` 场景（最大轮次 1），四款 Ollama 模型的表现：

| 模型 | 会不会调工具 | 单次模型调用 | 全程 | 答案质量 |
| --- | --- | --- | --- | --- |
| `qwen2.5:3b` | 会，2 次（根目录 depth=2 → frequencyAnaly/pom.xml） | 22 秒（含 1.9GB 冷加载）/ 54 秒 / 142 秒 | **3 分 39 秒** | 923 字，逐条列出真实依赖 —— Spring Boot 2.1.7.RELEASE、Oracle/Dameng JDBC、GeoTools、POI、OR-Tools 9.11.4210、protobuf 4.26.1，**逐项核对 pom 全部属实** |
| `qwen2.5:7b`（原默认） | 会，3 次（根 → frequencyAnaly → pom.xml） | 41–49 秒 | 5 分 28 秒 | 读了 pom，给出 `com.abrs` / `frequencyAnaly` / Spring Boot 2.1.7 等具体事实 |
| `deepseek-r1:8b` | 会，但只调 1 次就收尾 | 首调 4 分 48 秒（含 5GB 冷加载，且当时 7b 同时在内存抢 CPU），第二次 64 秒 | 5 分 52 秒 | **只看根目录就断言"没有 Java 源代码"**，实际是有 pom 的 Maven 工程；回答里还漏出思考标签 |
| `deepseek-r1:7b` | **不会**，一个工具都没调 | 2 分 52 秒 | 未跑完整任务 | 纯幻觉：凭空\"看到\"了 `config/config_common.py` 等不存在的文件 |

### 3b 的额外发现

- **快 34%**：3 分 39 秒 vs 7b 的 5 分 28 秒，且输出更长（923 字 vs 735 字）。时间构成：
  首次调用 22 秒（含冷加载）→ 第二次 54 秒（`depth=2` 的目录结果进上下文）→ 最终成文 142 秒。
  也就是说**大头仍是"读完 pom 后生成正文"**，换小模型主要压缩的是工具调用前的思考开销。
- **指令遵从更脆**：用极简提示词（"动手前先用 list_files 看目录"）时，3b 会反过来问用户"项目路径是什么"，
  一次工具都不调；把规则写死（"现在立刻调用 list_files，dir 传 .、depth 传 1，不要先提问"）才正常调用。
  说明**系统提示词里的强约束对小模型是必需的**，7b 在弱提示下也能自己调。
- **事实性合格**：本次没有出现 R1 那种凭空造文件名的问题，列出的依赖逐项可核对。

结论：**日常"看文件 + 下判断"的任务，`qwen2.5:3b` 性价比最高（快且准）；复杂多步任务仍用 `qwen2.5:7b` 更稳。**
两个 R1 都不划算：

1. R1 是推理模型，每次动作前先产出 770–1021 个思考 token；在纯 CPU 上等于把每次调用的成本翻倍，
   而它对"该多看几层目录"这件事没有任何帮助——8b 反而因为"想清楚了"就提前收尾，结论更浅。
2. `deepseek-r1:7b` 的工具调用能力基本不可用（不调工具、直接编），**不要**用它跑编码/分析场景。
3. Ollama 的 `/v1` 流式会把思考过程混进 `content`，页面会显示带思考标签的脏文本。
   已在 `ChatAgent.stripThinking` 里做兜底清理（有闭标签就切掉，只有开标签就当作没产出）。

想换模型自己对比，不用改文件：

```bash
# 换 3b（更快、日常分析够用）
java -Dmodel.name=qwen2.5:3b -cp "target/classes;target/lib/*" com.example.agentcore.Main web 8097

# 换 R1-8b（能调工具但结论浅）
java -Dmodel.name=deepseek-r1:8b -cp "target/classes;target/lib/*" com.example.agentcore.Main web 8097

# 想长期用：改 src/main/resources/agent.properties 里的 model.name
#   推荐 qwen2.5:3b（快）或 qwen2.5:7b（稳）
```

> 换模型前先 `ollama ps` 看一眼：同时驻留两个 7–8B 模型会互相抢 CPU 和内存，
> 实测这种状态下一次调用会被拖到 5 分钟以上，计时和体验都不真实。用完记得 `keep_alive:0` 卸载。

## 七、回答在一半断掉：模型把「计划」当成了结论

### 现象

页面上答到「根据 pom.xml 文件，这个项目使用了 Maven 构建工具。**接下来，我将分析 frequencyAnaly
目录下的内容**，以了解项目的具体架构和实现细节。」就结束了，后面再没有任何内容，也没报错。

日志里这一轮长这样（`18:12` 那次）：

```
路由 → general：没有明确的旅游或技术信号 → 单个助手直接回答
start 场景=general 最大轮次=1
→ 调用 list_files({"dir":".","depth":2})
← 返回 count=57
发言结束 · 546 字
done 轮次=1 消息=2 事件=300 增量=296 工具=1 停止=达到最大轮次 1
```

**不是卡死，也不是流断了**：模型确实"说完"了——它把"接下来我要干什么"写成了最终回答就收卷，
这一轮自然结束。三次原因叠在一起：

1. **路由落到兜底场景**：「分析一下这个项目」在 `TECH`/`CODE` 两张词表里一个词都没命中
   （`分析`、`项目`、`工程`、`源码` 都不在表里），只能走 `general`；而 `general` 的
   `maxRounds=1`，说完即结束，没有下一轮补救。
2. **提示词只管"答得准"，不管"做完"**：`general` 的角色设定是"直接回答用户的问题"，
   只读了 1 个目录就想收尾时，没有任何一句拦它。`readOnlyHint` 虽然给了
   "先列目录 → 再读构建文件 → 再看源码"的顺序，但没写"不许以计划句收尾"。
3. **小模型缺乏边做边说的自觉**：同样的任务，`qwen2.5:7b` 会连调 2–3 次工具再答；
   `qwen2.5:3b` 有时读一个目录就交卷。这是 3B 规模的典型弱点，不是这一家的毛病。

### 改了三处

| 位置 | 改动 |
| --- | --- |
| `Scenario.general()` | 角色设定加规则 6、7：看文件要连续看到能下结论；**禁止**用"接下来我将…"结尾，要继续就直接调工具 |
| `CodePrompt.readOnlyHint()` | 硬规矩加一条：还想看别的文件就现在调；一轮结束时必须有结论，而不是一句计划 |
| `ChatAgent` | 兜底纠偏：识别出"只写计划"的收尾后，追一句"现在就去做"，**最多追两次** |

兜底判定不是靠固定句式（试过，脆），而是三个条件同时成立才算：**将来时成分**（接下来/下一步/我将/我会）
+ **第一人称**（必须出现"我"）+ **动作动词**（查看/分析/读取/搜索/检查…）。
这样"建议你下一步先看调度模块""所以我会建议用 OR-Tools 求解"这类正常结论不会被误判——
前者没有第一人称，后者没有动作动词。误判的代价是让用户白等几分钟，所以宁可漏判。

### 三轮实测

| 时间 | 提示词 | 工具调用 | 字数 | 结尾 |
| --- | --- | --- | --- | --- |
| 18:12 | 改前 | 1（只列了目录） | 546 | 「接下来，我将分析…」→ 断在这里 |
| 08:27 | 加规则 6、7 | 2（列目录 + 读 pom） | 608 | 「我会使用 `search_code` 来查找…」→ 仍是计划句 |
| 08:35 | 加规则 + 兜底纠偏 | 4（含一次参数写错后的重试） | 2890 | 逐条列出依赖与版本，无计划句 |

第二轮值得记一下：提示词让模型确实多读了 pom，但它换了种说法收尾（"我会使用 search_code 来查找…"），
固定词表没覆盖到，说明**光靠词表堵不住，得靠"条件组合"或进程内兜底**。

### 这一轮为什么反而慢了（9 分 11 秒）

模型给 `read_file` 传了 `maxLines=800`，把 479 行的 pom 整份读进上下文（约 1 万 token），
之后每一次生成都要重嚼这 1 万 token——和第四章那个 `list_files` 吐 200 条是同一类问题。
已在只读提示里写清：构建文件读前 120–200 行就够，不要整份塞。

### 自查口诀

- 页面停在"接下来我将…"→ 就是这个场景，不是服务挂了；
- 日志看 `done` 行：`工具=1` 配一个很长的 `耗时`，说明工具没读够就收尾了；
- 想确认是慢还是断：看最后一条 `← 返回` 和下一条 `→ 调用`（或 `发言结束`）的时间差，
  中间模型在生成就是慢，直接 `发言结束` 就是答完了。
