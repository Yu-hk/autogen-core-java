# 提示词回归集

> 改提示词之前先跑一遍、之后跑一遍，两张表对得上才算没退化。

提示词是这个服务里最像"玄学"的部分。改一句「要连续看几个文件」，模型可能从读一个变成读十个，
也可能干脆一个都不读；而这种退化**不会让任何代码测试变红**——单测测的是代码路径，不是模型行为。
于是只能靠人肉试，试三个任务就以为改好了。

这套回归集把"人肉试"固化成 10 条固定任务：每条都写清楚**最少要调几次工具**、
**答案里必须出现哪些来自真实文件的事实**。改完跑一遍，数字下降就是退化，不用争论。

## 一、怎么跑

```bash
# 全量（10 条，CPU 上约 20–40 分钟）
mvn -o test -Dtest=PromptRegressionTest -Dprompt.regression=true

# 只跑其中几条（改提示词时常用来只看受影响的）
mvn -o test -Dtest=PromptRegressionTest -Dprompt.regression=true \
    -Dregression.only=java-version,packages

# 换模型对比（先在 3B 上跑通，7B/20B 才有意义）
mvn -o test -Dtest=PromptRegressionTest -Dprompt.regression=true -Dregression.model=qwen2.5:7b

# 换目标项目（默认是当前仓库；分析别的工程时用这个）
mvn -o test -Dtest=PromptRegressionTest -Dprompt.regression=true \
    -Dregression.workspace=D:/workspace/demo-project
```

**默认关着**：它跑真模型，一次半小时，放进 `mvn test` 会把每次构建拖死。
只有动了提示词、路由或工具描述时才手动开。

结果写到 `target/prompt-regression/report.md`（同时打到控制台）。`target/` 已 gitignore。

判定逻辑本身的单测（`PromptJudgeTest`，11 条）**在默认套件里**——回归框架自己坏了，
也必须有人知道。

## 二、10 条任务

| id | 问的是什么 | 工具下限 | 必须出现 | 守的是什么 |
| --- | --- | --- | --- | --- |
| `java-version` | pom.xml 要求哪个 Java 版本 | ≥1 | `17` | 最基础：连指定文件都读不到，后面全不可信 |
| `dependency-version` | langchain4j 依赖版本 | ≥1 | `1.22` | 验证读到的是变量值，不是把 `${...}` 原样抄回 |
| `packages` | `agentcore` 下有哪些子包 | ≥1 | `web` `tool` `agent` | 要看得见目录；一次工具都不调就编包名是典型退化 |
| `stream-timeout` | ChatAgent 流式调用等多久 | ≥1 | `10` | 从"哪个类"到"哪个常量"要跨一步 |
| `sse-resume-class` | 哪段代码做 SSE 断点续传 | ≥2 | `runsession` | 概念→代码的映射，光搜关键词不够 |
| `max-retained` | RunSession 保留窗口条数 | ≥1 | `6000` | 数字类事实最能验证"真读了"，3B 编数字很顺 |
| `error-codes` | ErrorCode 有哪几种 | ≥1 | 四个 code 全齐 | 少一个通常意味着只读了枚举一半就下结论 |
| `project-overview` | 这项目是做什么的 | ≥2 | `agent` | 最贴近真实用法；也是历史 bug 的原发地 |
| `web-file-count` | `web` 目录下有多少 .java | ≥1 | `13` | 数数必须靠工具；凭感觉给的通常整十整百，编不出 13 这么零碎的数 |
| `smalltalk` | 说说 SSE 是什么（**不该翻文件**） | 0（≤2） | `服务器` | 反向用例：概念题也去翻文件 = 工具推过头 |

**为什么问题写得像真人打字**：「这个项目用哪个 Java 版本」是好问题；
「请调用 read_file 读取 pom.xml 并提取 maven.compiler.release」测的是指令跟随，不是日常使用。

**为什么事实值都取自本仓库**：这样"看了文件"和"在编"可以分开——编出来的版本号不会刚好等于
`17`、`1.22`、`6000`。反过来说，**这些常量改了就要同步改任务清单**，这是好事，
说明回归集真的盯着代码。

## 三、判定

| 判据 | 说明 |
| --- | --- |
| 工具调用次数 | 少于下限 → 大概率在凭记忆答；多于上限 → 过度工具化（只有 `smalltalk` 管上限） |
| 必须出现的字符串 | 小写包含匹配。缺一个 = 没读到，或者读到了没写出来 |
| 回答字数 | 低于阈值 → "一句话交卷" |
| 计划句收尾 | 「接下来我将…」「我会使用 search_code 去…」——说要去做但没做 |

**计划句判定刻意不复用 `ChatAgent.endsWithPromise`**：那边是被测代码的兜底逻辑，
用它做判据等于自己证明自己对。回归集里独立实现一份。

判定实现上踩过两次坑，都记在测试里：
- 只看关键词 → 误伤「接下来我将分析 pom.xml。**分析结果：**…」这种**已完成**的回答。
  现在只看最后一句，且三个条件同时成立（将来时 + 第一人称 + 动作动词）。
- 漏了「我会使用…」这种改口 → 真实出现过的说法，漏了等于没判。

## 四、基线

跑出一次全绿之后，把工具调用次数记成基线，下次对比就能发现"还答得出来，但不再去看了"
这种最隐蔽的退化：

```bash
# 全绿之后追加这个参数，会在 target/prompt-regression/baseline.json 生成基线
mvn -o test -Dtest=PromptRegressionTest -Dprompt.regression=true -Dregression.writeBaseline=true
# 确认这份结果没问题，再拷进仓库
cp target/prompt-regression/baseline.json src/test/resources/prompt-baseline.json
```

报告里会多一列「基线」，并且当某条的工具调用**不足基线一半**时给出警告：

> ⚠️ 工具调用明显下降（不足基线一半）：`packages`：2 → 0 次

## 五、局限（写清楚，免得当成保证）

- **只管 general 场景**。装配复刻的是 `AgentWebServer.buildTeam` 里 general 那条路径
  （只读四件套 + 20 次迭代）。`coding` 场景要写盘、要编译，跑一条好几分钟且污染工作区，
  没放进默认清单。要加的话对着 `buildTeam` 的 `coding` 分支配一份装配即可。
- **温度 0 也挡不住全部随机性**。同一句问题跑两次，工具调用次数可能是 2 和 3。
  所以断言的是"至少 N 次"而不是"正好 N 次"，基线对比也只在**掉一半以上**时才告警。
- **不做语义判定**。答案说得对不对只靠"必须出现的字面值"来近似。要判"解释得好不好"
  就得上另一个模型当裁判，那是另一套东西。
- **不是性能测试**。报告里的耗时只用来发现"某条突然慢十倍"，不做阈值断言——
  机器负载一变它就红，那种测试没人会维护。

## 六、改提示词的标准动作

1. 改之前跑一遍全量，存下 `report.md`
2. 改提示词
3. 再跑一遍，两张表逐行对比
4. 工具调用下降 / 某条变红 → 先怀疑自己改松了，别急着怪模型
5. 确认提升后再更新基线

跳过第 1 步的话，第 3 步看到的数字**没有参照**，等于白跑。

## 七、实测记录：3B 上跑出来的东西（2026-10-28）

第一次跑完最该记住的一句：**首跑不是在看模型行不行，是在看判据行不行。**
10 条里红了 6 条，其中 2 条是判据写错、1 条是任务本身不可完成，只有 3 条真的是模型的问题。

### 7.1 仪器先修了三处

| 问题 | 现象 | 改法 |
| --- | --- | --- |
| `packages` 下限写成 2 | 它调 1 次 `list_files`、`web/tool/agent` 全答对，却被判失败 | 下限改 1（一次列目录就够） |
| `java-file-count` 问全仓 `.java` 数量 | 只读工具集没有统计能力，要一路 list 到底还会被截断 | 改问单目录（`web` 下 13 个） |
| 没有单条超时 | 一条任务读了 6 万字符的目录后，14 分钟还在生成，整批挂死 | 单条 240 秒上限（`-Dregression.task-timeout-seconds`） |

第二行那条要单独说：**判据写偏会把答对的判成错的，比漏判更有害**——它让人去改本来没坏的东西。

### 7.2 三轮提示词实验

| 轮次 | 改了什么 | `stream-timeout` / `max-retained` / `error-codes` | 结论 |
| --- | --- | --- | --- |
| 1 | 原提示词 | 0 次工具调用，答案都是**「我无法确认最新值」**（8 字） | 现成话被当成万能挡箭牌 |
| 2 | `general` 规则 2：把"实时信息"的边界写清 | 仍是 0 次；答案缩成**「查不到」**（3 字）；`max-retained` 编出「10」 | 换措辞没用，出口还在 |
| 3 | `readOnlyHint`：点名先 `search_code`、数数用 `list_files` | 每条**调 1 次** `search_code`，然后交卷 | 从"不查"变成"不会查" |
| 4 | 补两条：给了路径就直接读；搜**标识符**不搜中文问题 | `stream-timeout` PASS（2 次调用、20 秒）——但下一轮又 FAIL | 提示词能教会它"搜什么"，但教不会它"搜不到再换一轮" |

**结论一：提示词里任何一句现成的"我不知道"，都会变成模型最省力的答案。**
第 2 轮把「我无法确认最新值」改写成「只有真要联网的实时信息才说查不到」，模型立刻把后半句
当成新的模板，答案从 8 字缩成 3 字。**只要规则里留着一个"不知道"的出口，3B 就会走它**——
不是因为它判断了"这个查不到"，而是因为那句话比调工具省力。所以提示词里不要放可直接照抄的
拒绝句式，要写"先看手上有什么"。

**结论二：3B 的问题不是"不愿查"，是"不会查"。**
第 3 轮它确实开始搜了，但搜的东西是这样的（报告里留了原始参数）：

| 任务 | 它写的搜索词 | 代码里真实的名字 |
| --- | --- | --- |
| `stream-timeout` | `流式调用最多等\d+秒` | `STREAM_TIMEOUT_MINUTES` |
| `sse-resume-class` | `sse breakpoint` | `Last-Event-ID` / `pollAfter` |
| `max-retained` | `int maxNumWindows = \d+;` | `MAX_RETAINED = 6000` |
| `error-codes` | `ErrorCode code = [A-Za-z0-9_]+;` | `RunFailure.MODEL_UNAVAILABLE.code()` |

它**把用户的中文问题原样当成代码来搜**，而没有从问题里抽出那个标识符（`ChatAgent`、
`RunSession`）去搜。搜索一次不命中就交卷，这是 3B 的检索能力上限，不是提示词能补的。

**结论三：还有一类失败是"编"，比"查不到"严重得多。**
`project-overview` 只 `list_files` 了一层，就用 42 秒编出了一整段项目介绍：
「名为 `workflow-service-flow` 的服务」「服务流程图」「前端使用 Vue.js」——这个仓库里
一个都没有（前端是 React，也没有那个服务）。**没有一句来自它看过的文件。**
"答得自信而错误"正是通用助手最该防的失败模式，也是最难用字面断言抓住的
（这里只靠"答案里必须出现 `agent`"间接判到）。

**唯一稳定有效的一处改动**：按问题类型选工具的提示。`web-file-count` 从
"0 次工具调用 + 编一个数" 变成 "1 次 `list_files` + 答对 13"，一条提示解决一类问题。

### 7.3 由此得到的判断

- **3B 只在"路径已经给死"的问题上可靠**：`java-version`、`dependency-version`（问的是
  `pom.xml`）、`packages`（给了目录）三轮全绿；需要自己定位代码的 4 条，改三轮都一样红。
- **不要为让 3B 过测而继续加提示词**。第 3 轮已经证明：加"用搜索"它就搜，加"搜什么"它还是
  不会抽标识符。再往下就是给它写死每个任务的搜索词了——那不是提升，是把测试答案抄进提示词。
- 要让这批任务真的过，方向是换模型或加"搜索不命中就换词/翻页"的强制回路，不是继续调措辞。

### 7.4 7B 对照：这台机器上跑不出来

`-Dregression.model=qwen2.5:7b` 跑了 5 条，前两条都是**240 秒超时、0 次工具调用**——
第一次生成都没回来，谈不上检索质量。这台 20 核纯 CPU 机器上 7B 的生成速度是 3B 的四五倍慢，
单条不可能在 4 分钟内跑完。

所以这里没有"3B vs 7B"的质量对比，只有一条算力结论：**这套回归集在本机只适合 3B；
要量 7B/20B，得有 GPU 或换成云端模型**（`-Dregression.base-url` 指到云端即可，其余不变）。
把 7B 的超时写成"模型不行"是错的——那是把算力问题记到模型头上。

另外，Ollama 默认把加载过的模型一直留在内存里。跑完 7B 再跑 3B，两个模型同时常驻
（3B 2.8G + 7B 6G + 嵌入模型 1.2G），3B 的第一个回答能拖到 4 分钟都没出来。
换模型之前先把它卸掉：

```bash
curl -s -X POST http://127.0.0.1:11434/api/generate -d '{"model":"qwen2.5:7b","keep_alive":0}'
```

### 7.5 最难看的一条：回归集自己会污染答案

第 3 轮里 `sse-resume-class` 的回答是：

> 在 `prompt-regression.md` 文件的第 150 行，有提到类 `sse-resume-class` 负责 SSE 断点续传。

**它没读代码，它读了这套回归集的文档。** 任务 id、`mustMention` 里的字面值（`6000`、
`1.22`、四个 code）、判定依据，全都写在 `src/test/**` 和 `docs/prompt-regression.md` 里，
而这两处和被测代码在同一个工作区、被同一个 `search_code` 搜得到。
答案键和考卷放在同一个房间，这场考试就没意义——**而且它会给出"通过了"的假象**，
比失败更危险。

改法：跑之前把仓库复制一份到 `target/prompt-regression/workspace`，跳过
`.git` / `target` / `node_modules` / `docs` / `src/test`，让模型只看"用户真会看到的那个工程"。
显式传 `-Dregression.workspace=<别的工程>` 时不做复制（那是别人的仓库，只读工具也动不了）。

### 7.6 超时必须是"真超时"

第一版超时是用 `future.cancel(true)` 做的，**那是假超时**：线程被放弃了，但那条 HTTP 请求
还在生成，继续占着那个模型，后面每一条任务都排在它后面。实测第 9 条超时之后，本该 1 秒
返回的第 10 条也卡住了，整批变成"一条超时、后面全慢"。

改法是把同样这个上限也设到模型客户端上（`ModelConfig` 的最后一个参数），让请求自己断掉；
外面那层 `future.get` 只留作兜底，多给 30 秒。

### 7.7 3B 的波动：单次通过不可信

同一条 `stream-timeout`，在一次运行里 PASS（2 次工具调用、20 秒），换一次运行就 FAIL
（1 次调用、5 秒放弃）。温度已经是 0 也没用——**它翻的是"要不要再找一轮"这枚硬币**，
不是采样。所以：

- 不要把"这条跑过了"当作结论，要看它**三轮稳不稳**；
- 基线只在整套全绿时记录，否则会把一次侥幸固化成标准（见第四节）；
- 报告里那句 `工具 1 次` 比 `PASS/FAIL` 更有信息量——次数掉下来就是退化，比判定翻转早。

### 7.8 当前基线：4/10（qwen2.5:3b，2026-10-28）

干净工作区 + 真超时之后，跑出来是这样：

| 任务 | 判定 | 工具调用 | 用时 | 怎么失败的 |
| --- | --- | --- | --- | --- |
| `java-version` | ✅ | 1 | 57s | — |
| `dependency-version` | ✅ | 1 | 47s | — |
| `packages` | ✅ | 1 | 35s | — |
| `smalltalk` | ✅ | 0 | 13s | — |
| `stream-timeout` | ❌ | 1 | 6s | 搜了一次没命中，回"查不到" |
| `sse-resume-class` | ❌ | 1 | 5s | 搜了 `"sse breakpoint"`，没命中就交卷 |
| `max-retained` | ❌ | 1 | 7s | 搜了自造的正则，没命中 |
| `error-codes` | ❌ | 1 | 5s | 同上 |
| `project-overview` | ❌ | 1 | 14s | 只列了一层目录，没往下读 |
| `web-file-count` | ❌ | 0 | 240s | 一句话生成超 4 分钟（真超时生效） |

**能稳定通过的，全是"路径已经给死"的任务**：问 `pom.xml`、给了目录名、或者压根不用查
（`smalltalk`）。**需要自己定位代码的 6 条，一条都没过**，而且失败方式高度一致：
搜一次、没命中、交卷。

所以这份基线要说的话不是"3B 太差"，而是**3B 的能力边界在哪**：
它能读你指给它的文件，不能自己找到该读哪个文件。产品上对应两条结论——
1. 页面上"选目录 + 问具体文件"这类用法对 3B 是可靠的，可以放心用；
2. "分析一下这个项目"这类开放问题，3B 给不出可信答案（第 8 条只是把目录念了一遍），
   要么换模型，要么在提示词里先让它自己列出"我准备看哪几个文件"再逐个读。

**这套基线没有写进 `src/test/resources/prompt-baseline.json`**：4/10 不是一份可以拿来
"防止退化"的标准，把失败固化成基线等于承认失败是正常的。等换到能跑 8/10 的模型再记。
